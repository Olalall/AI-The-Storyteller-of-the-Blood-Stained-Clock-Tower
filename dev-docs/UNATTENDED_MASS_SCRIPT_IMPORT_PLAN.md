# 批量智能板子导入无人推进总计划

状态：**已冻结 / 第一批 10 板已完成 12.15 总验收**。  
日期：2026-07-19。  
语言要求：本文档和后续导入验收文档默认使用中文；角色稳定 ID 保留英文。  
适用范围：从“找到一个板子”到“这个板子能进入开局列表并用于智能配板、夜序和规则提示”的完整流程。  
不适用范围：真实 AI live 调用、官方魔典同步器、玩家端、自动跑完整规则、数据库/ORM、VPS 正式写入。

## 1. 一句话目标

把大量板子逐个变成可维护、可验收、可随机配板、可夜序使用的 `SmartScriptPack`，而不是把 JSON 和规则文案乱塞进前端。

## 2. 为什么需要总计划

如果只是“导入很多 JSON”，短期看很快，长期会出现：

- 每个页面都复制一份角色技能。
- 中文名、英文 ID、图标、夜序对不上。
- AI 配板不知道哪些模板是合法的。
- 新增一个板子要改多个页面。
- 夜间技能建议开始变成散落的角色 if/else。
- 后面想改一个角色规则，会不知道真源在哪。

所以批量导入必须走流水线：

```text
候选板子
-> 来源归档
-> 角色事实确认
-> 夜序确认
-> setup 规则确认
-> 模板库
-> SmartScriptPack
-> registry 接入
-> UI 可选
-> smoke 验收
-> 收口审计
```

## 3. 分层原则

### 3.1 总计划管“流程”

本文档只规定：

- 批量导入分几个阶段。
- 每阶段能无人推进到哪里。
- 什么情况必须停。
- 什么算可用。
- 如何防止架构膨胀。

### 3.2 批次计划管“名单”

例如：

- `SCRIPT_IMPORT_BATCH_01_PLAN.md` 管第一批 10 个板子。
- 未来可以新增 `SCRIPT_IMPORT_BATCH_02_PLAN.md`。
- 每批最多建议 10 个，超过 10 个必须另起批次。

### 3.3 单板目录管“事实”

每个板子的事实必须在自己的目录里：

```text
src/domain/scripts/packs/<script-id>/
  index.ts
  roles.ts
  night-orders.ts
  setup-rules.ts
  setup-templates.ts
  acceptance.md
```

不要把很多板子混在一个大文件里。

## 4. 批量导入阶段

## 4.1 阶段 A：候选板子池

目标：建立“可以考虑导入”的板子清单。

允许无人推进：是。

产出：

```text
dev-docs/script-import-candidates/
  <batch-id>.md
```

每个候选至少记录：

- 板子名。
- 作者。
- 来源 URL。
- 来源等级：官方基础版 / TPI 推荐 / TPI 收录社区脚本 / 作者发布 / 未确认。
- 是否适合 7-15 人。
- 预计复杂度。
- 首要价值：新手、长局、混乱、投票、夜间复杂、恶魔机制等。

不能做：

- 不能把候选板子直接加进开局列表。
- 不能把 AI 猜出来的规则当作来源。

验收：

- 候选清单有来源。
- 每个候选有是否进入本批的理由。

## 4.2 阶段 B：来源归档与内容 hash

目标：把要导入的板子资料固定下来，避免后面来源变化导致规则漂移。

允许无人推进：是。

产出：

```text
src/domain/scripts/packs/<script-id>/acceptance.md
```

必须记录：

- 来源 URL。
- 作者。
- 版本或抓取日期。
- JSON/PDF/夜序来源。
- 内容 hash。
- 未确认项。

不能做：

- 不能只写“来自官网”。
- 不能用没有来源的截图当唯一依据。

验收：

- `acceptance.md` 可读。
- source 字段在 pack 里可追踪。

## 4.3 阶段 C：角色事实确认

目标：确认本板所有角色的稳定事实。

允许无人推进：部分允许。

允许无人推进的内容：

- 整理角色清单。
- 建立 `roles.ts` 草案。
- 标记 `needs-review`。
- 补充明显来源证据。

必须停止或降级的内容：

- 规则冲突。
- 中文译名不确定。
- 技能生效时机不确定。
- 身份变化、阵营变化、疯狂、醉酒、中毒等高风险点不确定。

每个角色必须确认：

- 稳定英文 ID。
- 中文展示名。
- 英文名。
- 阵营。
- 技能文本。
- 首夜是否行动。
- 其他夜是否行动。
- 输入类型。
- 可能结果。
- setup 影响。
- 状态变化。
- 身份变化。
- 阵营变化。
- 是否需要玩家私密信息。
- 高风险说明。
- 知识状态。

验收：

- 没有角色只靠中文名当主键。
- 高风险角色不能标成 confirmed，除非来源已核对。

## 4.4 阶段 D：夜序确认

目标：首夜和其他夜顺序能被夜晚工作台直接读取。

允许无人推进：是，但必须保留来源。

产出：

```text
night-orders.ts
```

要求：

- 首夜和其他夜分开。
- 每项使用稳定 `roleId`。
- 不在夜序里写结算逻辑。
- 死亡、无需唤醒、只首夜/只其他夜由工作台投影处理。

验收：

- 在场角色能筛选当前夜序。
- 完整夜序仍可查看。
- 夜序和角色事实都来自同一个 pack。

## 4.5 阶段 E：setup 规则确认

目标：配板人数构成和特殊角色修正准确。

允许无人推进：部分允许。

必须确认：

- 7-15 人基础构成。
- 外来者增减。
- 爪牙/恶魔特殊修正。
- 恶魔伪装数量。
- 是否存在开局替换、额外角色、隐藏角色。

不能做：

- 不能在 UI 里临时写人数修正。
- 不能靠 AI 生成未验证人数构成。

验收：

- `setup-rules.ts` 有测试覆盖。
- 模板构成校验能识别错误人数。

## 4.6 阶段 F：模板库生成

目标：让每个人数能从合规模板里抽候选，而不是每局让 AI 从零编。

允许无人推进：是。

最低模板目标：

| 人数 | 初始最低 | 推荐目标 |
|---:|---:|---:|
| 7 | 3 | 8-12 |
| 8 | 2 | 6-10 |
| 9 | 2 | 6-10 |
| 10 | 3 | 8-12 |
| 11 | 2 | 6-10 |
| 12 | 3 | 10-15 |
| 13 | 2 | 6-10 |
| 14 | 2 | 6-10 |
| 15 | 3 | 10-15 |

模板必须包含：

- `templateId`。
- `playerCount`。
- `style`。
- `roles`。
- `bluffs`。
- `notes`。
- `verified`。

验收：

- 模板角色数量等于人数。
- 人数构成符合本板 setup 规则。
- 恶魔伪装不在场。
- 未验证模板不会被候选引擎返回。

## 4.7 阶段 G：SmartScriptPack 注册

目标：让板子进入统一 registry。

允许无人推进：是。

要求：

- 只注册 `confirmed` 或明确允许 `needs-review` 的 pack。
- 开局列表只显示可玩状态的 pack。
- UI 不直接 import 某个板子的内部文件。

验收：

- `registry.test.ts` 通过。
- `getScriptPack(scriptId)` 能返回完整 pack。
- 不存在重复 `scriptId`。

## 4.8 阶段 H：UI 可用接入

目标：用户能在开局流程选择该板子，并看到对应模板、夜序和角色提示。

允许无人推进：是，但必须跑 UI 测试。

要求：

- 选择人数 -> 选择板子 -> 填昵称/经验 -> AI配板。
- 不自动进入夜晚。
- 不自动发送身份。
- 换板子必须显式确认。
- 角色和夜序来自 registry。

验收：

- 对应单元测试通过。
- 需要时补 E2E。
- `npm run check` 通过。

## 4.9 阶段 I：单板收口审计

目标：确认这个板子没有引入架构债。

允许无人推进：是。

每个板子完成后检查：

- 是否新增巨型文件。
- 是否 UI 复制角色文案。
- 是否用中文名当主键。
- 是否引入自动结算 if/else。
- 是否把 `needs-review` 伪装成 `confirmed`。
- 是否有测试证据。

产出：

```text
src/domain/scripts/packs/<script-id>/acceptance.md
```

## 4.10 阶段 J：批次收口审计

目标：一批板子全部完成后，统一检查是否可进入下一批。

允许无人推进：是。

产出：

```text
dev-docs/SCRIPT_IMPORT_BATCH_<NN>_CLOSURE_AUDIT.md
```

验收：

- 本批每个板子都有 acceptance。
- 所有新增测试通过。
- 浏览器 smoke 或用户验收完成。
- `HUMAN_CHANGELOG.md` 已更新。

## 5. 无人推进队列设计

无人推进按“单板小闭环”推进，不按“先把所有板子的 roles.ts 都写完”推进。

正确节奏：

```text
一个板子：来源 -> 角色 -> 夜序 -> setup -> 模板 -> registry -> UI -> 测试 -> acceptance
完成后再进入下一个板子
```

错误节奏：

```text
先写 10 个 roles.ts
再写 10 个 night-orders.ts
再写 10 个 templates.ts
最后一起修爆炸问题
```

原因：单板闭环能及时暴露架构问题，批量横向铺开容易同时制造十倍错误。

## 6. 文件预算

每个新板子建议预算：

| 文件 | 建议上限 | 超限处理 |
|---|---:|---|
| `index.ts` | 120 行 | 只做组合导出 |
| `roles.ts` | 260 行 | 拆 `roles-town.ts` 等 |
| `night-orders.ts` | 160 行 | 拆首夜/其他夜 |
| `setup-rules.ts` | 180 行 | 抽纯函数测试 |
| `setup-templates.ts` | 260 行 | 按人数拆分 templates-7.ts |
| `acceptance.md` | 不限 | 文档可长，但要分标题 |

如果为了接一个板子导致共享文件超预算，必须先拆分，不继续堆。

## 7. 角色复用策略

同一个官方角色不能在多个板子里复制多份事实。

推荐方向：

```text
src/domain/roles/
  official/
    townsfolk.ts
    outsiders.ts
    minions.ts
    demons.ts
  community-overrides/
```

但是否现在拆 `src/domain/roles`，由第一个新增官方基础板 Trouble Brewing 的实现情况决定。若现有 `domain/scripts` 能承载，先不提前大重构。

规则：

- 可以先在 pack 内实现，发现重复后再抽共享角色库。
- 不允许同一个 `roleId` 在两个地方有不同技能事实。
- 中文展示名可以由本地化层覆盖，但稳定 ID 不变。

## 8. AI 接入边界

批量板子导入期间，AI 可以：

- 帮整理资料草案。
- 帮生成模板候选。
- 帮写模板说明。
- 帮生成 acceptance 草案。

AI 不可以：

- 单独作为规则确认来源。
- 把未验证模板标为 verified。
- 自动决定某个高风险规则。
- 自动把板子放入开局列表。
- 调用真实 provider，除非用户另行授权 `10.9-live`。

## 9. 可用定义

一个板子达到“可用”，必须同时满足：

1. 能在开局选择。
2. 能按 7-15 人至少关键人数生成模板候选。
3. 模板可手动调整。
4. 恶魔伪装不在场。
5. 夜晚工作台能按在场角色筛选夜序。
6. 角色技能展示来自统一事实源。
7. 日志记录不丢失、不复制第二状态源。
8. AI 提醒只作为草稿或建议。
9. `acceptance.md` 写清楚来源和未确认项。
10. `npm run check` 通过。

如果只能展示角色，但不能智能配板，不能叫“可用智能板子”，只能叫“导入草稿”。

## 11. 停止条件

任何阶段出现以下情况必须停止：

- 需要真实 API Key、真实网络调用或费用授权。
- 需要 VPS 写入、部署、端口或远端数据目录变更。
- 规则来源冲突且无法从可信来源确认。
- 用户明确表示某个中文名、规则理解或玩法方向不认可。
- 文件预算明显超限且继续堆会形成屎山。
- 需要大范围重构共享状态源。
- UI 需要新增第二套玩家状态或第二套夜序。
- 自动技能结算开始绕过说书人确认。

## 12. 每轮无人推进最终汇报格式

每完成一个板子或一个阶段，最终汇报必须包含：

- 本轮完成了哪个板子 / 阶段。
- 这个板子现在能做什么。
- 哪些角色或规则仍是 `needs-review`。
- 新增/修改了哪些文件。
- 跑了哪些测试，结果如何。
- 是否进入下一阶段。
- 如果停下，停下原因是什么。
