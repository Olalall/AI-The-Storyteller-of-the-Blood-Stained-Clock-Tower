# 设计目的

这份文档回答一个问题：**这个工具为什么长成现在这样。**

它不列功能，也不讲怎么用。它讲的是每一条看起来「多余的摩擦」「偏执的边界」
背后在防什么——因为这个项目里绝大多数争议，最后都归结到同一件事上。

想知道做了什么，读 [PRODUCT_VISION.md](PRODUCT_VISION.md)。
想知道边界在哪，读那三份 BOUNDARY。
想知道现在欠着什么，读 [G3_REVIEW_FINDINGS.md](G3_REVIEW_FINDINGS.md)。

---

## 一、它服务的那个人

线下血染钟楼的说书人。一局 12 人，三到四小时，他一个人要同时做四件事：

- 记住谁是什么、谁中了什么、谁昨晚做了什么
- 在每个夜晚按顺序叫醒十来个角色，给出正确的信息
- 白天主持提名与投票，裁定处决
- 在有人质疑「你上一夜是不是给错信息了」时，说得清当时发生了什么

前三件靠实体魔典和记忆能撑住。**第四件撑不住。** 一局打完，
没有任何人——包括说书人自己——能复原第 2 夜到底发生过什么。
争议因此无法收敛，复盘因此只能靠印象。

这个工具存在的唯一理由是第四件事：**让一局的每一个判断都留下可查的痕迹。**

其余所有功能都是为了让「留下痕迹」这件事不额外增加他的负担——
如果记录本身要花他半分钟，他在牌桌上就不会记。

## 二、一条贯穿全部决策的原则

> **工具记录说书人的判断，不代替他判断。**

这句话听起来是句正确的废话，但它在代码里是有牙齿的，
而且它解释了这个项目几乎所有反直觉的选择。

### 它否掉了什么

**否掉自动结算。** 工具知道 3 号是下毒者、知道他昨晚指了 7 号，
但它**不会**把 7 号标成中毒。因为「中毒」是一次裁定：
7 号可能被僧侣保护、可能是隐士、可能因为某条规则互动而不受影响。
一旦工具替他判了一次，说书人就再也不知道哪些状态是自己定的、哪些是工具猜的——
而那正是他最需要说得清的东西。

**否掉自动判胜负。** 一屏就能看到「恶魔已死、存活 3 人其中 2 邪恶」，
写一个胜负横幅的诱惑极大。但胜负是说书人宣布的，
工具显示客观计数可以，显示结论不行。

**否掉自动推进昼夜。** 相位之间只有一道门：交接卡。
环上的任何手势、抽屉里的任何操作都不推进相位。
因为「现在是白天还是黑夜」是牌桌上的物理事实，不是屏幕上的状态机。

**否掉 AI 落账。** AI 可以生成配板建议、结算建议、复盘草稿，
但它产出的永远是**草稿**。三段式文案钉死了这一点：
`生成建议` → `采用草稿` → `确认落盘`，禁止出现「应用」「执行」「AI 已处理」。

### 它要求了什么

**每一次权威状态写入都必须能追溯到一次说书人的显式动作。**
这就是为什么魔典上点一下座位不会改变任何东西——它只写草稿，
落账要再按一次确认，而且确认之后必须给回执。

「按下去毫无反应」在这个工具里是最坏的一种反馈：他会以为自己点上了。
所以拒绝写入时必须说出一句话，而不是静默失败。

**撤销是逆操作，不是回滚。** 撤销追加一条新记录，投影回到操作前，
但历史里两条都在。因为「他改了又改回来」和「他从来没改过」
在复盘时是两件完全不同的事。

## 三、为什么有两种模式

最初的设想只有一种：说书人手边有实体魔典，工具只做记录台。
这个假设对一半的场景是错的——很多人没有实体魔典，或者不想在牌桌上摊开它。

所以有了魔典模式：屏幕上多一张座位环，身份与标记都在上面。

**两种模式共用同一条数据路径。** 同一个 GameSession、同一条时间线、
同一个持久化 key。切换不产生任何记录，也不改变阶段。
魔典模式下，夜序、投票、AI 建议、配板全都以**辅助入口**的形式融进环的交互，
而不是在魔典之外再挂一套等价的全屏工作台。

这条约束不是洁癖。一旦按模式分出两套节点判定，两套数据模型就开始长了，
而它们迟早会对同一局给出不同的答案。

### 模式本身是出处元数据，不是行为开关

`session.hostingMode` 记录这一局当时是怎么主持的，**禁止任何 reducer 读它**
（有架构守门强制）。

理由是归档必须诚实：一局纯记录模式主持的对局，魔典上大半是空的。
不标注的话，回看的人会把「当时没人录」读成「当时没发生」——
而复盘正是靠这些空白与非空白做判断的。

---

## 四、为什么防窥是三级而不是一个开关

魔典模式带来一个纯记录模式没有的风险：**一屏就能看到整局的真相。**

所以有三级遮蔽：

- **L1 席位视图**（默认）：只有座位号、生死、中毒/醉酒。角色名与图标**不进 DOM**。
- **L2 揭示**：长按 600ms 才进得去，90 秒无操作自动落回。
- **L0 全遮蔽**：双指点画布立刻盖上，内容整段不进 DOM。

设计前提是「说书人会忘」：忘了盖上就把设备转过去、忘了自己还停在 L2 就去接水。
所以每一条自动落回都不是便利功能而是安全网，且**永不自动升到 L2**。

L1 下抽屉仍会显示当前唤醒项的角色名，这是**有意的**——
他正在处理的那一项本来就要看得见，纯记录模式下也一样。
L1 防的是「整块板子被一眼扫走」，不是「屏幕上不能有任何角色名」。

## 五、为什么座位环不能拖拽

这是整个魔典设计里最大的一次砍伐（砍掉约一半工程量），值得单独说。

自由拖拽画布看起来更强大，但坐标一旦持久化，标记归属就有**两个真值**：
按坐标就近算出来的，和按 seatId 记下来的。两者不一致时，
没有任何办法判定谁对——而这正是实体魔典最容易出错、也是工具最该消灭的那一类歧义。

所以：座位角度由人数唯一决定，标记按计算附着到 seatId，
session 里不存任何像素坐标。

## 六、为什么持久化这么偏执

魔典模式下，工具成了**唯一**的事实来源——实体魔典不在桌上了。
一份存档丢失，等于一局作废，而且是在三小时的对局进行到一半时作废。

所以有耐久性闸门（它是魔典写入功能的准入条件，不是加分项）：
快照轮转（主副本 + 最近 5 份）、启动崩溃恢复、多标签页单实例锁、
导出 JSON 常驻可达、破坏性操作前先快照。

「导出常驻可达」这条尤其要紧：它此前藏在「收尾 → 先存一份归档」后面，
而那条路在最需要它的时刻恰好走不通——打到一半、后端连不上、
或者刚看见「存档读不出」的时候。

## 七、为什么这里的测试写成这样

这个项目里，**测试写得对不对，比覆盖率重要得多。**

原因是它的核心卖点是「复盘可信」，而破坏这一点的 bug 往往不是崩溃，
是一条看起来正常、实际不对的记录。这类 bug 不会让测试变红——
除非测试专门盯着它。

所以有几条硬规矩：

- 每条测试的注释写「违反这条会发生什么」，不写「should work」。
- 禁止恒真断言、禁止期待值来自被测函数自身。
- 关键修复要做**变异验证**：把实现改坏，确认那条测试真的会红。
- 夹具要先确认它真能走到被测分支（`createPrototypeGameSession()`
  的 3 号座位出厂就 poisoned，是本仓最常见的假绿来源）。

以及一条这一轮才付出代价学到的：
**验证只用 `npm run check`**（lint && test && build && verify:architecture）。
单跑 `tsc --noEmit` 与 `tsc -b` 走的不是同一份配置，
而单测全绿盖不住类型层——[G3_REVIEW_FINDINGS.md](G3_REVIEW_FINDINGS.md)
开头记着这次的完整教训。

## 八、为什么有架构守门脚本

上面那些原则，光写在文档里守不住。它们会以「一个体贴的 useEffect」
「一个 helper 函数」「一个 token 类型上的 effect 字段」的形式悄悄长回来。

所以 `scripts/verify-architecture.mjs` 把尽可能多的边界**转化成依赖方向与类型形状问题**——
这两类可以 100% 静态验证，不依赖语义判断。目前守着的包括：

- AI 不得直连权威状态（state 目录禁止 import services/ai）
- 角色包必须是纯数据
- localStorage key 集中登记，禁止新增未登记的持久化真值
- 提示标记不得携带效果字段
- hostingMode 不得成为分支条件
- 主持模式偏好不得被渲染层读取（否则两个真相源会漂移）

加规则时的判据是：**能不能不靠语义判断就查出来。** 查不出来的，
写进 BOUNDARY 文档并在 code review 里逐条对照。

P0 前置修复、纯记录四批、G1 只读魔典、耐久性闸门、G2 魔典写入已完成并验收。

那个顺序是按「改完之后下一组才有守卫」排的，不是按严重度。

**允许永不做**——不做它，魔典模式依然完整可用。
