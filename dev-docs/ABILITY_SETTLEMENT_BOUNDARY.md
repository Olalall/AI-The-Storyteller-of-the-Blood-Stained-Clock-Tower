# 技能结算与 AI 建议边界

状态：设计冻结，待分阶段实现。  
目标：允许 AI/规则辅助结算，但不把项目做成自动规则引擎。

## 1. 产品定位

技能结算采用 A+B 组合：

- A：说书人手动记录是基线，任何技能都能不用 AI 直接记录。
- B：AI/规则助手可以根据当前局面生成结算建议、提醒和日志草稿。

最终权威动作仍由说书人确认。

## 2. 三层能力

### L0：手动记录

说书人填写：

- 发动者。
- 目标。
- 声称或猜测的角色。
- 说书人决定的结果。
- 给玩家的信息。
- 是否写日志。
- 是否影响状态。

L0 必须永远可用，即使 AI、网络、后端都不可用。

### L1：结构化建议

系统根据智能板子包和当前局快照提示：

- 这个技能通常需要几个目标。
- 是否需要选择角色。
- 是否可能改变身份、阵营、状态或死亡。
- 是否存在毒醉、疯狂、重定向、免疫、额外外来者等注意点。

L1 可以由本地规则知识生成，不调用真实 AI。

### L2：AI 结算草稿

AI 根据本次问题和上下文输出：

- 规则事实。
- 缺失信息。
- 推断过程。
- 推荐结论。
- 可选处理。
- 给玩家的信息草稿。
- 建议日志草稿。

L2 输出永远是草稿，不能直接改变 `GameSession`。

## 3. 推荐数据结构

```ts
interface SettlementDraft {
  draftId: string
  source: 'manual' | 'rule-hint' | 'ai'
  actorSeatId: SeatId
  roleId: RoleId
  input: AbilityInput
  suggestedOutcome: SuggestedOutcome
  statusEffects: StatusEffectDraft[]
  identityChanges: IdentityChangeDraft[]
  playerMessages: PlayerMessageDraft[]
  journalDrafts: TimelineEntryDraft[]
  missingFacts: string[]
  confidence: 'low' | 'medium' | 'high'
}
```

确认前：只能存在于草稿层。  
确认后：拆成时间线事件、状态投影、身份变更事件和可选玩家展示内容。

## 4. 身份、阵营、状态变化规则

确认后的变化立即影响当前投影，但不重写历史开局。

- 身份变化：追加 `IdentityChanged` 事件。
- 阵营变化：追加 `TeamChanged` 事件。
- 状态变化：追加 `StatusChanged` 事件。
- 死亡变化：追加 `DeathChanged` 事件。
- 更正：追加 `CorrectionEvent`，不覆盖原记录。

当前夜晚队列是进入夜晚时的人工确认快照。身份变化不会自动回滚或重排当前已走过的夜序；复杂链条只生成待办提醒，由说书人处理。

## 5. 复杂角色示例

这些例子用于提醒架构风险，不代表只支持这些角色。

### 赌徒

记录语义应是：

```text
6号赌徒猜测 8号 是某角色。
```

结算建议可以提示：猜对通常无事发生；猜错通常导致赌徒死亡。  
是否猜对、是否死亡由说书人确认。

### 舞蛇人

需要特别建模：

- 命中恶魔时可能交换身份和阵营。
- 原恶魔会得知自己成为新的舞蛇人。
- 原舞蛇人成为新的恶魔。
- 新的舞蛇人处于醉酒/能力不生效状态。
- 当晚变化立即影响身份投影，但技能使用时机要按规则处理。

这类角色不能靠简单“选择目标 -> 生效/不生效”表达完。

### 洗脑师

需要表达疯狂语义：

```text
你被洗脑成了某角色。你需要疯狂地证明自己是该角色，否则说书人可能执行后果。
```

洗脑师的信息给法既有规则约束，也有沉浸感文案空间；两者必须分层。

### 熬药女巫等复杂链条

如果产生新恶魔、旧恶魔被替代死亡、说书人随机刀等连锁效果，系统只能生成结算草稿和待办提醒，不允许自动执行整套链条。

## 6. AI 结果按钮

每个可结算技能都应有 AI 建议入口，但按钮语义必须清楚：

- `生成建议`：只生成草稿。
- `采用草稿`：把草稿填入本项表单，不写权威状态。
- `确认本项`：由说书人确认后才写日志和状态。

禁止按钮文案让人误解为 AI 已经完成裁定。

## 7. 后端边界

后端可以保存：

- 原始输入。
- AI 请求上下文摘要。
- AI 输出草稿。
- 说书人是否采用。
- 最终确认记录。

后端不应保存一套隐藏规则引擎状态，也不应让 AI 输出直接写入权威表。

## 8. 验收标准

- 关闭 AI 后，夜晚和白天仍能完整记录。
- AI 建议未确认前，玩家身份、状态、死亡、昼夜、日志都不改变。
- 所有 AI 建议都能不采用、修改后采用、仅记录或丢弃。
- 身份/阵营/状态变化有独立事件，历史日志可还原。
- 新角色接入前必须先完成角色级规则确认。

## 9. 魔典模式的越界判别

纯记录模式下「不自动结算」几乎是白拿的：工具根本不持有局面，想自动也无从算起。魔典模式把完整局面搬进了工具，这条边界从此只能靠可检验的实现约束来守。

真正的危险在于，它不会以「我们来做个规则引擎吧」的形式提交。它以一连串体贴的小优化长出来：夜间确认了击杀顺手把目标标死、加了中毒标记顺手把 `poisoned` 置真、票数达标顺手把人暂列、标记到了移除时机顺手清掉、阵营反转顺手改阵营。每一条单看都合理，评审时几乎找不到拒绝的理由——除非有成文判据。等它们累积起来，说书人已经分不清屏幕上哪些结论是自己下的、哪些是程序替他下的；而这个工具的全部价值恰恰建立在「这一切都是我判的」之上。

统一判据只有一句：**每一次权威状态写入都必须能追溯到一次说书人手势，且一次手势只能产生一次写入。**

下面 6 条是这句话的可对照形态，出现即越界。它们被写成 code review 与 `scripts/verify-architecture.mjs` 能逐条比对的样子，不接受「只是个小优化」「用户会喜欢」这类抗辩。

### 9.1 级联写入

一个 reducer case 在处理某个 action 时修改了它名字之外的状态。例：`add-reminder` 同时改了 `alive`。

判据——每个 case 的 diff 字段集必须是该 action 名字的字面子集。

这条最难靠人眼守住，因为越界甚至不需要改 reducer：只要在构造 action 的组件里多塞一个 op 就成立。所以它必须落成不变量测试——对任意 `confirm-player-state-change`，`after` 与 `before` 的差异字段集是 `ops[0]` 名字的字面子集，`ops` 长度恒为 1，系统不得因一条 op 派生第二条 op。多座位的同一手势按座位各写一条记录，共用 `batchId`。越过去之后，复盘时没有任何办法分辨一次点击里哪个字段是说书人的本意、哪个是程序附赠的。

### 9.2 派生值入库

把渲染层算出来的结论写回 session。存活数、票数门槛、是否达到多数、恶魔是否已死都可以显示，但一旦出现在 dispatch 的 payload 里就是越界。

判据——`majority`、`aliveCount`、`isDemonDead` 这类计算值只能进 render，不能进 action。

区别不在于这个数算得准不准，而在于它一旦入库就成了第二个真值：投影出来的存活数和存进去的存活数会在某次更正后分叉，之后没人知道该信哪个。计算值留在渲染层，它永远由权威状态推出来，永远不会过期。

### 9.3 定时/副作用推进

任何 setTimeout / setInterval / useEffect 触发的状态写入。白天计时器是唯一豁免，且它不写日志、不改状态（PRODUCT_VISION:18 已有此约束）。

判据——魔典相关目录下，**权威状态**（session / 时间线）的写入调用不得出现在定时器回调或 effect 体内；写入必须由事件处理器（说书人的点击、长按、确认）直接触发，调用栈上能指回一次手势。

这里管的是权威状态，不是屏幕。遮蔽级别在 90 秒无操作或页面失焦后自动回落、计时器每秒重绘，这些都由 effect 驱动，但它们不写 session、不进时间线、不改变任何人的身份或生死，因此不在本条的管辖范围内——它们改的是「你现在看得见什么」，不是「这局发生了什么」。

这条守的是「可追溯到一次手势」里的「手势」二字。定时器写权威状态的那一刻，屏幕前可能根本没有人：回执给谁看、谁为它负责都无法回答，而说书人下一次抬头看到的局面已经和他离开时不一样了。

### 9.4 标记即效果

提示标记（reminder token）的数据结构里出现 `effect` / `appliesTo` / `modifies` / `onNight` / `resolve` 之类字段，或放置标记会改变任何其它座位的字段。标记只能是贴纸：一个 seatId + 一段文本 + 一个来源角色，仅此而已。

判据——魔典 token / reminder 的类型定义文件中，禁止出现字段名 `effect`/`effects`/`appliesTo`/`modifies`/`onNight`/`onDeath`/`resolve`/`trigger`；放置或移除标记这一手势的 diff 字段集只含标记集合本身（与 9.1 同一条不变量测试覆盖）。

出处类字段不在此列：`sourceRoleId`（这张贴纸是哪个角色贴的）与 `placedInSegmentId`（贴在哪一段）记录的是它怎么来的，不参与任何判定。判别看的是字段有没有语义效果，不是字段有几个。一旦标记带上效果，实体魔典上那张纸片就变成了可执行的规则片段，说书人从「贴纸提醒自己」变成了「给引擎下指令」，而他不再有机会在贴之前改主意。

### 9.5 能力可执行化

角色知识从数据变成函数，出现 `applyAbility(session) => session`、`resolve(state)` 这类签名。角色包一旦能拿到局面并返回局面，它就已经是一台推演机，剩下的只是谁去调用它、什么时候调用。

判据——`src/domain/scripts/packs/**` 与 `src/domain/role-knowledge/**` 禁止 import `GameSessionState` 或 `features/game-session/**` 的任何类型，禁止出现 `=> GameSessionState` 返回签名。角色包与角色知识是纯数据与纯函数，需要局面信息时由调用方投影成入参传进去。这条已由 `verify-architecture.mjs` 的 `pack-no-session-state` 规则强制，违反即 CI 失败。

之所以能做成依赖方向问题，是因为语义上的「这算不算自动结算」永远有得辩，而「角色包认不认识 GameSessionState」没得辩。

### 9.6 AI 直写

AI 的输出可以被直接 dispatch。最省事的实现就是让 AI 返回一个 action、前端照单 dispatch——那一步是全部边界的崩塌点，它同时废掉了「AI 只给草稿」（第 2 节 L2）和「每次写入都追溯到一次手势」两条。

判据——① `src/features/*/state/**` 下任何文件禁止 import `services/ai` 或 `features/ai-*`，已由 `verify-architecture.mjs` 的 `state-no-ai-import` 规则强制，违反即 CI 失败；② AI 侧类型只能产出草稿结构（`SettlementDraft` 及与它平级的魔典操作草稿），不得产出 action 或 op；③ 说书人点击确认之前，魔典上不存在任何实心标记，导出的 session 里不存在对应记录。

AI 结果进入权威状态的唯一路径是：组件层取到草稿 → 渲染成可辨认的草稿态 → 说书人点击确认 → 由确认手势构造 action。这条链上少任何一环，AI 就从顾问变成了第二个说书人。

## 10. 魔典模式下的胜负、昼夜与死亡

AI_AUTHORITY_BOUNDARY 已经写明 AI 不判定胜负、不切换昼夜。魔典模式让这两条比过去更脆弱，因为诱惑不再来自 AI，而来自「屏幕上都算出来了，顺手显示一下」：一屏就能看到恶魔已死、存活 3 人其中 2 邪恶，写一个胜负横幅几乎不需要新代码；说书人又会长时间停留在同一个界面上，「顺手加一个自动切夜」的需求会自然浮现。

这三条不是新边界，是老边界在魔典语境下的重述，各自附一条可对照的判据。

### 10.1 胜负

魔典视图可以显示客观计数（存活数、已死数、阵营已知数），但禁止显示任何形式的结论性判定（「邪恶获胜」「善良只剩 X 人，恶魔胜利条件已达成」「胜负条件已满足」）。判据——UI 文案中不得出现胜/负/获胜/结束条件达成等词，除非它出现在说书人已手动选定胜方之后的回执里。

差别不在措辞客气不客气，在于计数是事实、判定是裁决。工具报出「邪恶获胜」的那一刻，局面的最终解释权就从说书人手里交了出去。而钟楼里几乎每条胜利条件都有角色能改写它，工具算错一次，整局的结论就是错的，且现场没有人会去复核一个看起来这么笃定的横幅。

### 10.2 昼夜

相位推进的唯一入口仍是交接卡（黄昏 / 黎明 / 收尾），魔典视图上的任何座位操作、标记操作、夜序操作都不推进相位；夜序光标的前进仍需说书人显式选择「停留 / 下一位」（AI_AUTHORITY_BOUNDARY:15）。判据——魔典组件树中不得出现 dispatch 相位类 action。

交接卡是相位之间唯一的门，也是全部不可逆动作的唯一落点（UI_REDESIGN_PLAN:46）。魔典模式继承这道门，不另开侧门。绕过之后「现在是第几夜」会出现第二个推进来源，而相位是全部记录的归属依据——归错一次，那一夜的记录就永久挂在了错的段上，复盘时无法分辨是记录错了还是相位跳了。

### 10.3 死亡

魔典上的「裹尸布 / 死亡态」切换是一次独立手势，不得由夜间结果、投票结果或标记自动触发。UI_REDESIGN_PLAN:135 已就此立过规矩（「绝不能由夜间结果自动推死亡」，黎明播报只做差分提示），魔典模式沿用：可以提示「本夜 2 项记录标注死亡结果，状态未更新」，不能替说书人更新。

判据——死亡字段的写入只能来自以死亡命名的手势 op；夜间结算确认、投票结算、标记放置这三类 action 的 diff 字段集里不得出现死亡字段（与 9.1 同一条不变量测试覆盖）。差分提示逐条列出、逐条采纳，不提供「全部应用」。

死亡是这局里最不可逆、最公开、也最容易被守护/免疫/替死类能力改写的一个字段。夜间记录里写着「击杀 3 号」和 3 号真的死了之间，隔着说书人对整晚链条的裁定；把这一步自动化，等于让工具替说书人宣布了一件全场都会看到、且当场无法撤回的事。

## 11. 撤销是逆操作，不是回滚

魔典模式引入大量高频、低成本、无表单确认的手势：点座位切死亡、贴标记、长按删除。误操作概率远高于表单式记录，因此必须有撤销。而撤销最诱人的实现——存一份 state 快照、点一下换回去——恰好绕过第 4 节的事件追加体系，让时间线不再能还原真实操作历史，直接损坏复盘与争议回溯这两个核心卖点。争议回溯尤其致命：玩家赛后质疑「你是不是把我标错了又改回来」，能回答这个问题的唯一凭据，就是那两条都还在的记录。

**撤销必须实现为追加一条 CorrectionEvent（ABILITY_SETTLEMENT_BOUNDARY:86），投影结果回到操作前，但历史里两条记录都在。禁止实现为 state 快照回退或从时间线删除条目。**

判据（逐条可查）：

- 撤销路径最终调用的是既有的更正追加机制（`appendCorrection` / `correctionOf`，见 `src/features/game-session/state/timeline.ts`），不是任何形式的 `setState(previousSnapshot)`。
- 撤销前后时间线条目数只增不减：任意一次撤销的条目数差值必须为 +1，出现 0 或负数即越界。
- 不存在删除入口——没有任何 action 能移除一条已落盘条目。
- 耐久性快照（`botc-copilot-session-snapshot-v1`）只服务于崩溃恢复与破坏性操作前留档，禁止被撤销按钮当作回滚源。「都是回到之前的状态」这个错觉是本条最常见的破口：崩溃恢复丢的是本来就没写成的东西，撤销抹掉的是确实发生过的操作。
- 回执带里 3.5 秒内的即时撤销走同一条路径，不因为「还在回执窗口内」就允许悄悄抹掉原记录。

代价要说在前面：这样做出来的时间线会比说书人的记忆更啰嗦，一次手滑会留下两条记录。这是有意的。档案的用途不是好看，是在赛后被人质疑时能逐条对上——一条能被清理干净的历史，等于没有历史。
