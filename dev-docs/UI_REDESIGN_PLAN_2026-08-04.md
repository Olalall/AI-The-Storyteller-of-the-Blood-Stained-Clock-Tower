# UI 排版与流程优化方案

- 日期：2026-08-04
- 基准：钟楼百科 429 页快照（`data/wiki-ground-truth/`）+ botc.games 前端产物逆向（Unofficial Digital Grimoire，同领域最成熟工具）
- 方法：5 个界面审计 + 1 个设计系统审计 + botc.games 对标 + 百科主持流程基线，共查出 **109 条问题（high 51 / medium 49 / low 9）**；
  再由三名设计者按不同第一原则各出一版方案（流程连续性 / 魔典视图中心 / 减量抽象），经评审排序后取最优并移植其余两版的可取主张。
- 结构化数据：`data/wiki-ground-truth/compare/ui-analysis.json`

---

## 一、诊断：「乱」的五个根因

1) 相位推进被切成三段跳：夜里点「检查并关闭」→ onExit 回 Dashboard → 在第三屏块找「进入白天」（App.tsx:31-44、NightCloseFooter.tsx:25、Dashboard.tsx:182-193）。而百科流程里真实存在的「黄昏」「黎明」两个交接步骤在工具里全部 missing，于是每次交接都退化成一次导航操作加一次纯记忆负担。
2) 视图按数据表而不是按流程划分：App.tsx:17 的 View = dashboard|night|day|timer 四个互斥全屏，连倒计时都是与工作台并列的第四视图——想把大字倒计时给玩家看必须离开白天工作台，票型草稿只能靠暂存兜底。
3) 上下文不跟随说书人：夜间看不到白天事实（createNextNightRun.ts:183 把 history 置 undefined，回溯型能力全靠脑记）、白天没有「本局记录」入口、Dashboard.tsx:128-145 的「当前阶段」卡在段落关闭后显示的是下一个阶段——三处都在同一个「我在哪、上一步发生了什么」上失灵。
4) 视觉权重与节奏反相关：最大最亮的是全夜不变的「第三夜」、250px 装饰转盘、hero 大字（night-workbench.css:33/642、dashboard.css:1306），而每 30 秒换一次的「当前是谁、下一步做什么」和主确认动作被压到折叠线以下，连续操作变成「滚动—找按钮—确认—滚回」的循环。
5) 护栏与不可逆动作错位：一夜一次的「确认关闭」贴在一夜十几次的「确认并下一位」下方约 20px 且同为金色 primary；离开守卫因 progress 判定错误（NightWorkbench.tsx:82）从不触发；窄屏 role=status 被 night-workbench.css:599 的 display:none 吃掉。节奏最紧的时刻恰恰没有回执，最不该点的按钮恰恰最好点。

## 二、目标信息架构

顶层收敛为 2 个视图 + 1 个交接层，App.tsx 的 View 由 4 个变为 'deck' | 'archive'。

A.「主持台 Deck」——唯一常驻工作视图，占据全部主持时间。
  · 顶部 PhaseTrack（48px sticky）：黄昏 · 夜 · 黎明 · 白天 · 提名投票 · 处决 六节点，当前节点是全屏唯一暖金；节点下一行 12px 显示「第N夜/第N天」。右端两枚常驻入口：「本局记录 N」与「收尾」。
  · 中部「步骤台」：内容随当前节点切换，但容器与滚动位置不变——夜=唤醒卡流（现 CurrentWakeCard），白天=讨论/提名/举手/暂列的单列步骤序列，黄昏/黎明=交接卡。
  · 底部单一 StickyActionBar：固定 [次要动作] [还差提示] [唯一主动作 + 推进开关] 契约，位置永不随节点变化。
  职责唯一：产出并确认本相位的记录，以及在说书人点确认时推进相位。

B.「本局档案 Archive」——只读与更正，覆盖式 page，关闭后精确回到主持台原节点原滚动位。
  收纳现 Dashboard 的非入口部分（玩家状态板、配板、发身份、开场白、切换板子）、本局记录/日记、结束归档与复盘。职责唯一：查与改历史，不承担任何相位推进。

C. 交接层 PhaseHandoff——页内覆盖卡，不是新视图：黄昏交接、黎明播报、白天收尾、局终收尾。它是相位之间唯一的门，也是全部不可逆动作的唯一落点。

切换方式：主持台与档案由 PhaseTrack 右端单一入口互切（档案是覆盖层，主持台不卸载）；相位推进只在主持台内由交接卡的主动作完成，永不经过首页；已完成节点可点开只读回看，顶部持续挂「回看中 · 修改不会前推」条。倒计时不再是视图，降级为白天步骤内的「投屏」全屏遮蔽层。

## 三、改造清单（16 项）

### 1. 新增共享组件 src/components/ui/PhaseTrack.tsx + 挂载点 src/app/AppFrame.tsx  `M`

**改什么**：新建 48px sticky 阶段轨道，六节点（黄昏/夜/黎明/白天/提名投票/处决）横排，每节点为 44px 高触控目标，含图标+中文标签+状态（done 冷灰实心 / current 暖金实心 / next 描边 / 回看中加青色下划线）。节点下方一行 --type-meta 显示「第N夜」。右端固定两枚 compact 按钮：「本局记录 N」（N 取 projectEffectiveTimelineEntries 长度）与「收尾」。轨道数据由 session.phaseSegments + activeNightRun 推导，不引入新状态。同时把 night-header（96–160px）、day-workbench__header（约190px）、dashboard hero（150–240px）三套页头压成单行 32px 的「本局名 · 剧本 · 人数」。

**为什么**：说书人抬头 0.5 秒要回答的只有一个问题：现在在哪一步、下一步是什么。目前这个答案分散在三套页头、两个都叫「夜序」的数字和一张会说谎的 hero 卡里。轨道把它压缩成一行且全局位置不变，同时回收约 200–400px 首屏给主任务。

**依据**：百科《规则概要》二/三节的昼夜循环节点；botc.games 顶栏常驻 Town Info（Alive/Dead/Votes/Majority）零交互恒定位置的做法。

```
Before:
[Dashboard]  eyebrow/h1/hero 大卡(240px, 「当前阶段 第3天」可能是错的)
[Night]      night-header 96~160px + 转盘 250px + 通知 38px  → 主任务在 1000px 处
[Day]        header 约190px（h1 与 480px 计时卡平分）
After:
[全局 sticky 48px]  ● 黄昏 — ◉夜 第3夜 — ○ 黎明 — ○ 白天 — ○ 提名投票 — ○ 处决      [本局记录 42] [收尾]
[各页头 32px 单行]  乌鸦渡口 · 12人
[步骤台]            当前唤醒卡（首屏即主任务）
```

**风险**：轨道 sticky 与各 feature 的 @container 断点体系叠加，可能在 620/760 缝隙里与现有页头残留双层吸顶；需先删旧页头再挂轨道，不能并存。

### 2. src/App.tsx（View 类型与三个 enter* 函数）  `L`

**改什么**：View 由 'dashboard'|'night'|'day'|'timer' 收敛为 'deck'|'archive'。新增 deck 状态 { phaseNode: 'dusk'|'night'|'dawn'|'day'|'vote'|'execution' }，由 phaseSegments 推导初值。enterNight/enterDay 不再 setView，改为「打开对应交接卡 → 说书人确认 → dispatch open-phase-segment → setPhaseNode」。archive 以 Sheet presentation="page" 覆盖渲染，deck 保持挂载（滚动位置与草稿全部留存）。删除 'timer' 视图分支与 Dashboard.tsx:172-175 的「公聊倒计时」按钮。

**为什么**：四个互斥全屏是「上下文丢失」的机制性来源：每次切换都卸载组件、丢滚动位、丢正在看的那一行。改成一个不卸载的主持台后，跨相位与查记录都变成覆盖与替换内容，而不是导航。

**依据**：botc.games 的 /play 画布从不卸载，所谓「切换视图」全是覆盖其上的浮层；且它把玩家可见面物理隔离成独立页面，而说书人自己的操作面从不分裂。

```
Before: dashboard ⇄ night ⇄ day ⇄ timer 四个互斥全屏，每次切换整棵子树卸载
  夜结束: [关闭本夜] → onExit() → Dashboard(滚到第三屏) → [进入白天]   （3 次导航 + 1 次找按钮）
After:  deck 常驻 + archive 覆盖
  夜结束: 轨道 [收尾] 或最后一项确认后自动浮出「黎明播报」卡 → [已宣布睁眼 · 进入第3天]   （1 次确认）
```

**风险**：DayWorkbench/NightWorkbench 目前依赖 onExit 卸载来清理局部 state（nominationTarget、pendingResolution、openPanel）；改为常驻后需显式在相位切换时重置，否则会把上一天的 pendingResolution 带进新的一天。

### 3. 新增 src/features/hosting-deck/handoff/DuskHandoff.tsx（步骤台的 dusk 节点）  `M`

**改什么**：页内交接卡，三段只读清单 + 一个主动作：① 上一白天结论回执（处决/无处决、谁死亡、门槛与票数，取自 timeline）；② 黄昏准备清单（本夜为首夜/其他夜、需翻面提示、上一夜「持续至黄昏」的效果到期候选、需要预先想好的三张伪装与错误信息——每条只是勾选备忘，勾选不写任何状态）；③ 本夜队列预览（前 3 项 + 总项数 + 待核对数）。底栏唯一主动作「所有玩家闭眼 · 开始第N夜」，次要动作「回上一天补记」。

**为什么**：黄昏是百科里明确存在、工具里完全缺失的一步，现状是说书人在 Dashboard 上凭记忆完成。把它做成交接卡，既补上流程缺口，又给「白天→夜」这次跳转一个自然的落点，替代掉「返回首页找按钮」。

**依据**：《规则概要》二.1 准备夜晚阶段（翻面夜序表、增删提示标记、预先筹划伪装与错误信息）；《规则概要》三.3 末段「花三十秒左右准备夜晚阶段」。

```
Before: 白天点[结束今天] → 回 Dashboard → 自行回忆要翻夜序表/要想伪装 → 点[进入夜晚] → 直接落在第一张唤醒卡
After:  白天收尾确认后 → 页内浮出
  ┌ 黄昏 · 准备第3夜 ─────────────────┐
  │ 上一天：处决 7 号（已死亡） 4票/门槛4  │
  │ □ 夜序表已翻到「其他夜」            │
  │ □ 到期效果已核对：僧侣保护(第2夜)     │
  │ □ 伪装三张已想好                    │
  │ 本夜队列 9 项 · 待核对 1            │
  │ [回上一天补记]     [闭眼 · 开始第3夜] │
  └──────────────────────────────┘
```

**风险**：清单极易滑向「代办」。必须严格保持勾选项不写 session、不改队列、不生成记录，只做本地 UI 备忘并在离开时丢弃；文案统一用「请核对」而非「已处理」。

### 4. 新增 src/features/hosting-deck/handoff/DawnHandoff.tsx（步骤台的 dawn 节点）  `M`

**改什么**：黎明播报卡：以「黄昏那一刻的生死快照」与「当前 projectCurrentPlayerStates」做差分，用 --type-page-title 级大字列出本夜死亡与复活的座位号（无变化时明确显示「本夜无人死亡，仍要宣布」）。下方一行冷青护栏文案「只报生死，不报原因」。再下方是核对提醒条：「本夜有 N 项确认记录标注了死亡类结果，但玩家状态未更新」，附「去更新状态」跳玩家状态页（仍需说书人手改）。主动作「已宣布睁眼 · 进入第N天」，次要动作「回夜间补记」。倒计时式 5–10 秒缓冲以只读进度条呈现，不阻断按钮。

**为什么**：黎明是全流程里唯一一次说书人必须当众开口播报的信息，也是工具里 missing 的一步。做成差分卡后，说书人不需要在脑内比对「夜里我确认了什么、谁真的死了」，也天然把「夜→白天」这次跳转收进流程内。

**依据**：《规则概要》二.2「等待五到十秒」「宣布这个夜晚死亡和复活的玩家（相对黄昏而言状态变化的才宣布），但不告诉原因」；《夜晚行动顺序一览》「黎明」。

```
Before: 夜里最后一项确认 → [检查并关闭] → 二次确认 → onExit → Dashboard → [进入白天]；死了谁全靠回忆
After:
  ┌ 黎明 · 第3夜结束 ────────────────┐
  │ 死亡   ⑦                          │
  │ 复活   —                          │
  │ 只报生死，不报原因                  │
  │ ⚠ 本夜 2 项记录标注死亡结果，状态未更新 [去更新] │
  │ [回夜间补记]   [已宣布睁眼 · 进入第3天] │
  └──────────────────────────────┘
```

**风险**：差分依赖说书人已在夜间手动改过状态，否则会播报「无人死亡」。因此核对提醒条是必需项而非可选项，且措辞必须是提示不是断言；绝不能由夜间结果自动推死亡。

### 5. src/features/day-workbench/DayWorkbench.tsx 主体版式  `M`

**改什么**：把 day-workbench.css:32 的两栏并排（提名卡 | 举手卡）改为单列「步骤序列」：讨论(计时) → 提名 → 举手 → 暂列 → 处决/无处决。同一时刻只展开一个步骤，其余折成 44px 高摘要条（如「① 提名 · 3号提名7号 ✎」），点摘要条回退编辑。提名与举手座位网格在展开态使用 repeat(auto-fill, minmax(56px,1fr))，保证 ≥52px 触控。步骤内的确认（记录本轮票型 / 记录处决）全部改由底部 StickyActionBar 承载，pendingResolution 确认条改为接管底栏而不是追加在页面尾部。

**为什么**：「步骤 1 / 步骤 2」的编号说先后、并排布局说同时，这个矛盾让说书人视线在两列间来回跳。改成序列后，屏幕上任何时刻只有一件事，且与真实提名投票的时序一一对应；确认条也不会再落到屏幕外让人重复点击。

**依据**：《规则概要》三.2 提名与投票的严格时序（受理提名 → 辩护 → 计票 → 判定 → 下一个提名）；botc.games 的提名/投票是一个居中浮窗里的单一焦点流程，不并排。

```
Before（宽屏两栏，提名卡下方大片空底色；确认条追加在最底部，常在屏外）
  ┌ 步骤1 选择提名 ┐ ┌ 步骤2 记录举手 ┐
  │ [提名人][被提名]│ │ 门槛[4] 座位×12 │
  │ 座位 6 列×50px │ │ 举手3 死票0     │
  └───────────┘ └───────────┘
  … 暂列结果 … （滚动）… 处决确认条（屏外）
After（单列序列，一次一步）
  ① 讨论 · 公聊 03:12               ✎
  ② 提名 · 3号提名7号                ✎
  ③ 举手  ← 展开中：座位网格 56px，举手3 / 门槛4
  ④ 暂列 · —
  ─────────────────────────
  [稍后]        还差：门槛未达      [记录本轮票型]
```

**风险**：折叠会让「我还能不能改上一步」变得不明显；摘要条必须带铅笔图标与可点态，且回退编辑时不清空后续步骤已填内容。

### 6. src/features/day-workbench/components/DayTimer.tsx + PublicChatTimerPage.tsx + App.tsx  `S`

**改什么**：删除独立 timer 视图。DayTimer 增加「投屏」按钮，点击后以全屏遮蔽层（复用 PublicChatTimerPage 内容，presentation=page 覆盖层）显示大字倒计时，层内只有时间、阶段名和一枚「收起」；退出后精确回到白天步骤台的原步骤原滚动位。同时补齐 DayTimer.tsx:53 的空洞：公聊超时后渲染「重新开始公聊 / 回到私聊 / 重置」三选一，与全屏页保持同一套按钮集。

**为什么**：「把大字倒计时转给玩家看」是每局必做动作，现在的代价是整个白天工作台消失、票型草稿只靠暂存兜底——这是最典型的跨视图跳转导致的上下文丢失。改成遮蔽层后，主持台一直在下面活着。

**依据**：《规则概要》三.1 白天讨论；botc.games 把玩家可见面做成独立页面而说书人操作面从不卸载的原则（此处玩家可见面是临时遮蔽层，因为本项目不做玩家常驻端）。

```
Before: 白天工作台 →[返回本局]→ Dashboard →[公聊倒计时]→ 全屏页 →[退出]→ Dashboard →[进入白天]→ 从头找步骤
After:  白天步骤台 → DayTimer 上的 [投屏] → 全屏大字层 → [收起] → 回到原步骤原滚动位
```

**风险**：遮蔽层必须真正遮住秘密信息（不能只是半透明），且退出层的按钮不可与主确认按钮同色同位，避免在把平板拿回手里的那一刻误触确认。

## 四、分批落地

分三批，每批 2–3 周，批与批之间可独立上线。

第一批「骨架：让相位成为导航」（PhaseTrack、App 视图收敛、底栏统一契约、HostNotice、危险动作出栈、还差顺序修复）
验收标准：
· 从第 1 夜连续主持到第 2 夜，全程不出现 Dashboard，导航次数从 6 次降到 2 次（两张交接卡的主动作）。
· 在 520px 逻辑宽度单手竖握下，nightWorkbenchReducer 的五条 guard 回执 100% 可见且可被屏读读出；display:none 对 role=status 的引用为 0。
· 误触「结束本夜/结束今天/结束对局」的最短路径 ≥ 2 次点击，且终点按钮为 variant="danger"；主确认与破坏性动作的垂直间距 ≥ 96px 或不同屏区。
· 空草稿进入气球驾驶员类项目时，提示为「还差：选目标」，结果区全部按钮不可点。
· iPad 竖屏 820×1180 下，夜间主任务（目标区）首屏可见，确认按钮位于视口底部固定位。

第二批「交接：补上黄昏与黎明」（DuskHandoff、DawnHandoff、白天步骤序列化、倒计时投屏、记录入口归一）
验收标准：

## 五、botc.games 对标结论

### 它是什么

## 一、路由层（真正的页面切换只有这几个）
从 bundle 里能确认的路径：`/`（首页/开局向导）、`/draw`（抽牌）、`/play`（魔典主视图）、`/night-order`（夜序表，可打印/扫码）、`/player`（玩家手机端，独立客户端）、`/distribute`（发牌会话）、`/town.html`（**独立页面、独立 bundle**，玩家可见的"城镇视图"）、`/faq`、`/privacy`。
更新日志明确记录了一次架构决策：*"Moved Town outside of the App container to its own page. This removes unused and confusing UI elements that don't do anything, and gives more space to the town view itself."* —— 玩家可见面被**物理隔离成另一个页面**，而不是同一 app 里的一个 tab。

## 二、主流程是线性状态机，不是自由导航
Setup（选剧本 → 选角色 → 定人名/座位）→ Draw（抽牌）→ Play（魔典）→ End Game。
- Setup：三张官方剧本大卡（Trouble Brewing / Bad Moon Rising / Sects and Violets，各带一句难度描述）+ Custom Scripts（URL / 文件 / JSON / botcscripts.com 全库 / 高级按角色检索）。角色数校验用一条 overfill 进度条 + 文案 `select_more_roles:"Select {count} more roles to continue"` / `too_many_roles:"Remove {count} roles to continue"`。
- Draw：四种分发方式并列 —— Bag（点袋子抽）、Tokens（平铺牌面自选）、Mobile（扫码到手机）、Manual/Garden（后台指定，`garden_draw`：预设抽牌顺序，"给玩家随机的错觉"）。
- Play：`gamePhase` 从 `assign` 进入正式对局；顶部有 Day/Night 与轮次计数，可前后翻页回看历史。

## 三、`/play` 内部：**一个画布 + 三层浮层**，没有第二个"主视图"
主视图只有**一个**：`.grimoire-canvas`（黑色贴图背景，夜晚叠 `night-clouds` 云层渐变）。所谓"切换视图"全部是覆盖在它之上的浮层，画布本身从不卸载。

- Settings：Token Size、Reminder Size（两条独立滑杆）、Abilities、Travellers、Fullscreen、Official/Playtest Icons、About

## 七、明确不做

- 不做玩家常驻端、不做实时同步的公共屏、不做手机扫码发牌——本工具只在说书人设备上，玩家可见内容只以临时全屏遮蔽层（倒计时投屏）形式出现。
- 不做数字魔典画布、不做可自由拖拽的提示标记、不做座位环的形状编辑——实体魔典仍是主局面视角，本工具不再造第二张桌面；座位环若出现也只是只读索引。
- 不自动结算规则：不自动改身份/阵营/死亡/毒醉、不自动判胜负、不自动推进昼夜。PhaseTrack 只做导航与「建议下一步」，任何相位推进都必须由说书人在交接卡上点主动作；黄昏/黎明清单只提示不代办。
- 本次不新增旅行者、流放、疯狂、登记（当作/register）等领域模型——它们是真实缺口但属于数据层工程，本方案只在交接卡与状态栏预留插槽，不承诺行为。
- 不做全量 CSS 重写：只清理主干四个文件（dashboard / night-workbench / day-workbench / game-end）中与流程主干相关的死代码与未定义 token；setup、ai-settings、script-library 的样式债留待后续。
- 不引入卡片原语、表单原语、elevation/宽度/断点 token 的完整设计系统重建——这是正确的方向但与本次「流程连续性」主张不同轴，只在本次触及的组件里就近收敛，不做横扫。
- 不改动 AI 的能力边界与提示词：AI 仍只产出可被否决的草稿，本次只调整它在界面上的位置（结果只出现一份、依据只留一行、取消独立 AI 卡片）。

### 评审否决项（含「看起来很酷但违反定位」的提议）

- 【定位重罚】不要把 SeatRing 做成跨昼夜常驻的『全 App 唯一局面视图』。PRODUCT_VISION 明写『不是第二套官方魔典，不复制官方面板的完整空间局面』『以官方/实体魔典为主要空间视角』，ui-design-system.md 也写『角色 PNG 与圆形 Token 只保留给 RoleDisc，避免把座位操作误解为另一套魔典』。即便只读、无 PNG、不可拖，把座位环升为顶层持久视图就等于要求说书人同时维护桌面摆放与屏幕摆放两套局面——这正是定位刻意回避的成本，也是本轮最像『很酷但会把工具变成第二个数字魔典』的提议。座位环若要存在，只能作为单玩家页/记录页里的只读索引，不得常驻、不得成为选人主入口。
- 【定位重罚】不要做可拖拽画布、Circle/Ellipse/Rainbow 布局选择、环上放角色 PNG、环上直接摆提示标记——这些是同一条线更深处，一旦开始就无法回头。
- 不要用『数字键盘计票』取代逐座位举手记录。raisedSeatIds 的逐人留痕与死亡票逐座位标注是记录台的证据链，也是 AI 复盘的输入；为了少点几下而只留总数，是拿本产品的本体换输入速度。双阈值显示可以抄，输入模型不能换。
- 不要让记录页的阶段回看去『重建该阶段末的完整局面状态』。timeline 不足以重建的字段会被投影函数猜出来，而这个猜测会以权威只读态呈现给正被玩家质疑的说书人。只回看已写下的记录条目；状态快照若要做，必须先证明数据充分，无法重建的字段宁可留空。
- 不要整体删除 NightPlayerCarousel。它在 ui-design-system.md 的业务组件清单里，PRODUCT_VISION 也明写夜间借鉴播放器的『当前播放/上一首/下一首/播放列表/进度』认知。正确做法是减重不删除：按 reduce-first 恢复窄屏 196px（当前 :567 的 226px 与 :576 的 196px 都被 :643 的 250px 覆盖）、删掉 ::before 椭圆台面与 ::after 光晕、把上下位预览的裸箭头（42px，低于 44px 且误触即进预览态）换成带标签的可点区域。
- 黎明播报卡绝不能由夜间确认结果自动推断死亡。它只能对『说书人已手改的玩家状态』做黄昏快照差分，并以提示条（不是断言）指出『本夜 N 项记录标注了死亡类结果，但玩家状态未更新』。一旦从技能结果自动推死亡，就是 PRODUCT_VISION 明确排除的自动结算。
- PhaseTrack 不能实现为单一线性相位指针。昼夜记录段合同写明『一个开放的白天段与一个开放的夜晚段可以同时存在，便于说书人按现场情况自由补记』『进入、浏览、预览都不创建记录段，也不自动切换阶段』。轨道必须允许两个段同时为 open、允许在任一已开放段内补记，当前节点只是『建议下一步』的高亮而非锁；交接卡的主动作只推进 UI 焦点，是否 dispatch open-phase-segment 要与现有 App.tsx:37/42 的时机重新对齐（当前一进入就开段，本身就与合同有出入，应顺带收敛为首次权威保存才开段）。
- 黄昏/黎明清单的勾选项一律不得写 session、不得改队列、不得生成记录，离开即丢弃，文案统一用『请核对』而非『已处理』。任何让清单变成待办系统的演进都会滑向代办。
- 不要新增 --space-22/26/34 等档位来『修复』未定义 token。代码里出现过 22/26/34 恰恰证明档位太多而非太少；固化它们就是把漂移写进规范。
- 首夜爪牙信息/恶魔信息第一版不要为『多座位对象』扩 WakeItem 类型。它会波及 projectWakeDraft、gameRecordProjection 与 AI 建议链路，与本轮 UI 改造耦合。第一版做无目标的纯记录卡 + 勾选清单（伪装三张仅记录不校验），多座位建模单独立项。
- 不要做玩家常驻端、公共屏 Town View、扫码移动发牌、实时同步、多人协作说书、跨设备会话——三份方案都正确排除了，此处再确认：任何『把一块屏常驻留给玩家』的形态都出界。倒计时投屏只能是临时全屏遮蔽层，且必须不透明、秘密内容不进 DOM、收起按钮不与主确认同色同位。
- 不要把 timer 继续留作第四个顶层视图，但也不要让 PublicChatTimerPage 顺势发展成玩家端雏形——它降级为白天步骤内的遮蔽层后，功能边界锁死在『大字时间 + 阶段名 + 收起』三件事。
- 不要在早期批次做全量 stylelint 开启与断点全量归并（16→3）。前者会产生数百条报错淹没信号，应逐规则 opt-in、先开零争议的『禁未定义 var』；后者会大面积改变现网断点行为（iPad 竖屏 768 目前在 setup 与 game-end 里落在相反的命中位置），必须排到最后一批并配六宽度逐页截图对照。
- 不要引入 CSS Modules / Tailwind / CSS-in-JS 或组件库，也不要做卡片原语之外的『完整设计系统重建』。本轮用共享原语 + 命名前缀 + CI 守门压住症状即可，模块化迁移单独评估。
- 不要新增旅行者/流放、疯狂状态位、registerAs 登记异常等领域模型。它们是真实的百科覆盖缺口，但属数据层工程，与 UI 改造耦合会让所有低风险承诺失效；交接卡与状态栏可预留插槽，不承诺行为。

**🔴 high · 状态反馈｜中毒/醉酒/标记/死亡的生死指示被整体 opacity:0 隐藏，状态只剩颜色**

- 证据：dashboard.css:1510-1515 对 .dashboard-player-seat--poisoned/--drunk/--impaired-stack/--marked 下的 .dashboard-player-seat__life 一律设 opacity:0；dashboard.css:1639-1643 又对 :not(--dead) 变体追加 visibility:hidden。被隐藏的正是 PlayerStatusBoard.tsx:46-49 里的 HeartPulse/Skull 图标和 <em>死亡</em> 文本。全文件 1741 行内没有任何规则把 opacity 复原。直接违反 ui-design-system.md:55「存活、死亡、中毒、醉酒、标记不能只靠颜色区分」。
- 后果：一张「死亡+中毒」的座位卡，骷髅图标和红色「死亡」二字都是 opacity:0，死亡只剩深红背景在表达；一个只被打了标记（--marked）的活人，连心跳图标都没了，卡上没有任何生死线索。暗光下背景色差本就最先失真，说书人扫一眼 12 张卡数存活人数会数错，而处决/胜负判定全靠这个数。

**🔴 high · 状态反馈｜最大的那张「当前阶段」卡，在阶段结束后显示的是下一个阶段**

- 证据：Dashboard.tsx:108-111 段落关闭后 state 变 'done'；Dashboard.tsx:128-131 的 currentStage 回退链找不到 current/open 就退到 'next'；Dashboard.tsx:144-145 直接渲染 <strong>{currentStage.label}</strong><em>{currentStage.meta}</em>。第3夜 closedAt 之后，卡片字面读作「当前阶段 / 第3天 / 下一步」。同时 aria-label 用的是另一套文案 summary「第3夜已结束，下一步第3天」（Dashboard.tsx:115,140），视觉与读屏结论不一致。违反 ui-design-system.md:62「不再使用两个含义不明的『当前』」。
- 后果：全屏最大、字号最大（4.35rem）的元素在说谎：说书人刚结完第3夜抬头，卡上写着「当前阶段 第3天」，但天还没开。被玩家围观时这是当众的信息错误，说书人要么照着念错、要么当场愣住去翻记录确认自己在哪个阶段——而这张卡存在的唯一理由就是免去这次确认。

- 证据：hero 卡金色渐变+内发光（dashboard.css:1266-1274）、卡内金色胶囊 meta（1309-1319）、3 个纯装饰金点（1359-1372）；5 个平级次要按钮里「发身份」单独镀金（.dashboard__identity-entry, css:72-78）；主入口的 .dashboard__phase-icon 金色圆环（css:109）；座位卡 --drunk 整卡琥珀色（css:1556-1561）。设计系统把暖金定义为「当前焦点」色（ui-design-system.md:5）。
